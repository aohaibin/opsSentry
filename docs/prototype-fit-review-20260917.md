# 原型设计符合性评审：《远程运维部署助手》

**评审对象**：`docs/remote-ops-ai-prototype.html`
**评审时间**：2026-09-17

## 四、问题清单

### P0 — 直接影响「部署助手」定位成立

1. **部署模块没有「部署过程」的画面。**
   现状是「目标卡片 + 配方模板 + 空态部署组」三段式，全部是**结果态**。缺失的关键画面：
   - 流水线阶段（拉码 → 构建 → 制品 → 分发 → 软链切换 → 健康检查）
   - 实时构建/发布日志
   - 制品与版本树（`releases/ + current` 的可视化）
   - 发布审批与安全闸门的联动入口
   产品名里的核心词是「部署」，但这块是 17 个模块里投入最少的一个。

2. **环境维度缺失。**
   `生产环境` 只以**标签文本**出现（第 630、4548、5793 行），没有 `dev / staging / prod` 的一等公民模型。连带缺失：
   - 环境级审批策略（预发可自动、生产必须人工）
   - 环境级凭据隔离
   - 环境级部署目标绑定

3. **品牌命名四不像。** 同一份原型里并存四个名字：

   | 出现处 | 名称 |
   |--------|------|
   | 侧边栏 Logo（第 207 行） | **Reeve** |
   | 部署路径（第 2108 行） | `/opt/reeve/stacks/...` |
   | 页面 title（第 6 行）、MCP 名（第 7546 行） | **OpsSentry** |
   | `tauri.conf.json` productName | **运维助手** |
   | `tauri.conf.json` identifier | **com.opsentr.yunwei**（拼写疑似应为 opsentry） |

   对外交付前必须统一，否则后续 icon、安装包、MCP 配置、审计报告都会带着不一致的品牌串。

### P1 — 影响可交付质量

4. **331 个 `onclick` 中 43 个是纯 `alert()` 占位**，其余为 mock 函数。审批通过、回滚、批量执行、部署触发全部是弹窗文案。作为原型可接受，但**不能作为验收基线**——评审时无法验证状态流转。
5. **无多用户与角色模型。** 全文「权限」11 处、「角色」1 处，无登录页。而原型最重的两块（审批闸门 + 审计日志）本质上都需要「谁批的、谁执行的」这个主体。
6. **部署组是空态。** 原型里最有编排价值的设计（把前端静态站 + 后端网关 + 异步任务组合成「生产全栈发布组」，勾选即发）只有一张占位空状态，没有展开态。这是应该重点补的画面。
7. **移动端缺失。** 全文仅 1 处提及。运维审批天然适合移动端触达。

### P2 — 工程与体验

8. 17 个一级导航对 1440×900 桌面端偏重，收折后成为 68px 宽的图标 Dock，可发现性依赖 tooltip。
9. 原型技术栈（Tailwind CDN 3.4 + Lucide CDN + 原生 `switchTab`）与项目栈（React 19 + Ant Design 6 + Tailwind 4 + Vite）不同，**只能作视觉参考，不能直接搬代码**。
10. 已实现的 3 个页面（servers / workbench）已改用 Ant Design 组件 + `glass-card` 样式，视觉上并未严格复刻原型——后续需要明确「以原型为准」还是「以 AntD 为准」。

## 五、建议

| 优先级 | 建议 | 理由 |
|--------|------|------|
| 高 | 「部署与发布」从第 7 位提到第 2–3 位，补齐流水线画布 + 实时日志 + 制品/版本树 + 一键回滚 | 产品名核心词，当前最弱 |
| 高 | 补 `dev / staging / prod` 环境模型，环境级审批策略与凭据隔离 | 受控运维的前提，也是「助手」能自动化的边界 |
| 高 | 统一品牌命名，同步修正 identifier 拼写 | 影响安装包、MCP 配置、审计报告 |
| 中 | 明确「助手」交互范式：是否需要「对话即运维」主入口，把 17 个模块降级为 Copilot 的能力后端，导航收敛到 5–6 个 | 决定产品是「平台」还是「助手」 |
| 中 | 补登录 + 角色模型 | 审批与审计缺少主体 |
| 中 | 部署组补展开态设计 | 编排是差异化亮点 |
| 低 | 用可交互的 React 页面替换 `alert` 占位，建立可验收基线 | 原型阶段可不做，进入 Phase 2 前应做 |

## 六、结论

- **「远程运维」部分：符合，甚至超出。** 资产、终端、SFTP、批量、AI 诊断、凭据金库、出口脱敏、审批闸门、审计日志、告警，10 个能力域齐备，安全模型（trusted/approval/denied + HMAC 审计链）想得很细，可以直接支撑 Phase 2–8 的开发。
- **「部署」部分：基本符合。** 7 大部署配方 + 原子软链 + 回滚的设计方向正确，但缺少过程态画面，深度不足以支撑「部署助手」这个主词。
- **「助手」部分：不符合。** 当前是一个 17 模块的重平台，任务导向的助手感弱。
- **命名：不符合。** Reeve / OpsSentry / 运维助手 / com.opsentr 四处不一致，需尽快统一。

**给开发计划的动作**：在继续 Phase 2 之前，先回答两个问题——（1）产品到底是「平台」还是「助手」？（2）「部署」是主功能还是附属功能？这两个答案会直接改变后续 6 个 Phase 的模块排序和优先级。
